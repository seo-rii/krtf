# 검색·JSON 생성 안정성·독립 문단 평가 후속 큐

기존 [HF 생성 비교](../reports/hf_qa_retry_20261017/ANALYSIS.md)에서 검색 근거 손실,
작은 pack 개선, 형식 오류와 동일 프롬프트의 응답 차이를 관찰했다. 후속 큐는
검색 입력 개선과 생성 안정성을 구분하며 새 대형 모델을 추가하지 않는다.
질문·정답·조건·예산·채점은 생성 전에 동결한다.

## 1. 독립 기사 검색 비교

TyDiQA 한국어 원천의 고정 revision과 SHA-256을 재사용한다. 기존 생성 128질문,
준비 pool 384질문, 이전 근거 평가 256질문, 독립 문단 평가의 parent article과
내용 해시를 제외한다. 근접 중복이나 모델 사전학습 중복까지 배제한 것은 아니다.

처음 목표한 SPAN 56·YES/NO 8·무응답 64 구성은 이 제외 조건에서 고유 기사 수가
부족했다. 실패 inventory를 보존하고, **생성 전에 SPAN 40·YES/NO 8·무응답 80개**로
명시적으로 수정했다. 총 128질문·128기사는 유지하며, 양성 48개와 음성 80개의
분모를 별도로 보고한다. 이전 기사 제외를 완화하거나 결과를 보고 표본을 고르지 않는다.

| 조건 | 선택 방법 | gold 사용 |
|---|---|---|
| `lexical` | 기존 질문 어휘와 원문 구간의 유사도 | 없음 |
| `bm25` | 단어·한글 bigram의 BM25 점수, k1=1.2·b=0.75 | 없음 |
| `adjacent` | lexical 중심 구간에 앞·뒤 원문 구간을 함께 고려 | 없음 |
| `oracle` | 양성의 원래 정답 문단 전체 하나, 음성은 lexical과 동일 | **진단용으로만 사용** |

모든 조건은 원문 최대 3구간·3,000문자, 두 실제 토크나이저 각각에서 원문
1,536토큰 이하라는 공통 상한을 쓴다. 실제 소비 토큰이 같다는 뜻은 아니다.
Oracle도 원래 문단 전체가 들어가야 하며 정답 주변을 잘라 만들지 않는다.
이 용량 조건을 만족한 표본에 한정한 진단이다. Oracle은 배포 가능한 검색기가 아니다.

기존 128질문은 개발용 CPU 진단으로 사용하고, 새 기사에서는 세 검색기 모두를
고정 비교한다. 근거 보존율만 보고 최종 승자를 고른 뒤 같은 test를 재사용하지
않는다. 실제 답변 EM·근거가 보존된 정답·무응답·토큰 비용을 따로 측정한다.

두 모델에서 128질문 × 4조건, **1,024회**를 실행한다. 모두 동일한 근거 전용
정책과 자유 JSON 생성을 사용한다.

## 2. JSON 스키마 강제 생성과 반복

이전 생성 평가의 128질문을 사용해 `retrieved`와 `ktrf_pack`의 원래
`system`·`user`를 정확히 유지한다. 추가 주입은 기존 `should_inject` 결과를
그대로 보존한다. 이 표본은 이미 확인한 자료이며 새 독립 검증셋이 아니다.

각 문맥을 자유 생성과 JSON Schema 강제 생성에서 3회씩 실행한다. 스키마는
`answer` 필드 하나만 허용하고 문자열 또는 null을 받는다. 형식 강제는 의미적
정답·올바른 기권·등록된 entity ID를 보장하지 않는다. 서버가 스키마 요청을 거부하면
오류로 기록하며 자유 생성으로 자동 대체하지 않는다.

두 모델에서 128질문 × 2문맥 × 2생성 방식 × 3회, **3,072회**를 실행한다.
온도 0·seed 0·thinking off·출력 128토큰·stateless batch 1이다. 조건 순서는
질문별로 회전한다. 반복을 별도 질문처럼 취급해 표본 수나 신뢰도를 부풀리지 않는다.
질문별 평균 정답률, 반복 일치율, 같은 프롬프트 조건 사이의 차이, 형식 오류와
유효 응답 쌍의 helpful/harmful을 함께 보고한다. 실패한 쌍은 별도로 남긴다.

## 3. Resolver 출력 없이 작성한 실제 문단 gold

원천에서 먼저 뽑은 **24개 기사 각각의 원문 문단 하나**, 총 5,845 codepoint를
주석한다. 전체 Wikipedia 기사에 대한 완전 주석은 아니다. 원문에서 길이가
120~1,200 codepoint인 첫 문단을 선택하며 용어 포함 여부로 고르지 않는다.

고정 170-entity 사전과 명시적인 조직·국내 광역행정구역을 범위로 삼았다. 두 AI
주석자가 문단 전체를 읽고, resolver 출력을 보지 않은 상태로 각각 모든 범위 내
mention과 무언급 문단을 판단했다. 원본 주석 두 개와 이견 4문단의 명시적 조정을
보존하고 gold·원문 offset·문서 해시를 봉인한 뒤 `fast`와 `commit`을 실행한다.
이는 사람이 검증한 gold가 아니며 공통 모델 편향이 남는다.

문단은 parent article별 개발·보정·test 각 8개로 분리한다. 등록 대상은 총 4개,
미등록 조직 등 NIL은 46개이며, 보정 partition에는 등록 대상이 없다. 따라서
보정 학습을 하지 않고 `INSUFFICIENT_DATA`, `coverage_valid=false`로 남긴다.
모든 관측 full-surface가 SAME이어서 파생 의미 guard를 검증한 표본도 아니다.
이 작은 탐색 평가의 오확정 0건을 운영 위험 보장으로 해석하지 않는다.

## 실행·수집

CPU 검색 준비·실제 두 chat template의 토큰 예산·독립 문단 평가·고정 코드의 전체
테스트를 먼저 확인한다. GPU 큐는 Gemma의 검색→반복, Qwen의 검색→반복 순서이며
모델별 runtime 하나를 재사용한다. 총 GPU 요청은 **4,096회**다.

GPU와 전용 loopback port가 준비될 때까지 기다리며 다른 작업을 종료하지 않는다.
명시적인 시작 전 메모리 부족 오류만 최대 3번 재시도한다. 생성된 답변은 재시도·수정하지
않는다. 원본 요청·응답·채점·source archive·CPU 증빙의 해시와 manifest seal을
검증한 뒤 같은 코드로 다시 채점한다. 공개물은 집계·실행 증빙이며 원문과 개별 답변은
ignored private 경로에 남긴다. 현재 main이 origin/main과 동기화된 경우에만 결과를
정확한 파일 경로로 커밋·푸시한다.
