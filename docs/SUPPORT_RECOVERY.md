# 근거 복원과 문맥 판정의 승인 상한 비교

2026-10-22. 기존64문서의 [CPU oracle 진단](../reports/support_cpu_20261022/ANALYSIS.md)에서
정상32건 모두 정답 후보가 검색됐다. 정답 ID를 넣어도 기존 production occurrence
검증 상한은23건, 네 속성의 같은 문단 근거를 요구하면7건이다. 두 모델 모두 실제
승인7건에 도달했다. 이 진단은 정답을 사용하는 검증기 능력 분석이며 모델 성능이나
운영 승인을 나타내지 않는다.

## 실험 다섯 가지

1. **CPU 상한 분석:** 탐지·검색·기존 승인·근거 검사·모델/참조 오류를 단계별로 분리한다.
2. **근거 결합:** 같은 문단과 여러 문장·문단의 출처 좌표가 있는 근거를 비교한다.
3. **속성 판단:** 네 속성 모두 필수, 관찰된 속성의 충돌 검사, 적극적 지지와 충돌 검사를 비교한다.
4. **동음 약칭:** 문맥으로 구분되는 후보를 production과 실험용 shadow 판정에서 따로 측정한다.
5. **새 용어군:** 앞의 진단에서 선택한 한 방법을 새96문서·12개 용어군에서 기준선과 비교한다.

## 8가지 진단 조건

| 근거·속성 방식 | 기존 승인 검증 | 실험용 shadow 검증 |
|---|---|---|
| 같은 문단·네 속성 필수 | `paragraph_all_production` | `paragraph_all_shadow` |
| 여러 근거·네 속성 필수 | `multispan_all_production` | `multispan_all_shadow` |
| 여러 근거·관찰된 속성 충돌 검사 | `multispan_observed_production` | `multispan_observed_shadow` |
| 여러 근거·적극적 지지와 충돌 검사 | `multispan_supported_production` | `multispan_supported_shadow` |

각 조건은 같은 실제 resolver 후보, 완전한 원문·정의·적용 범위·발생 위치를 사용한다.
이번 기준선에도 새 출처 귀속·모순 검사가 공통 적용되므로, 이전 근거 묶음 실험의
7건과 숫자만 직접 비교하지 않고 이 실험 안의 기준선과 paired 비교한다.
근거 ID는 문서·snapshot·요청한 발생 위치와 서버의 문자 위치에 묶인다. 다른 대상에
귀속된 속성, 직접 부정된 값, 인용 속 문자열, 파생 직책을 기관으로 읽는 경우를
차단하는 규칙을 별도로 기록한다. 출처가 없는 속성을 참이라고 간주하지 않는다.

기존 승인 검증 결과와 각 실험용 판정은 모두 보존한다. shadow 조건은 모호한
후보를 추가 판정할 수 있지만 **실험용 승인 모의 결과**이며 실제 실행 권한을
부여하지 않는다. 운영 라이브러리의 승인 계약을 변경하지 않고, 실제 동작도 실행하지
않는다. 규칙의 속성 소유 추적과 모순 검사는 제한된 휴리스틱이며 의미 함의 보장이 아니다.

## 자료와 선택 규칙

진단은 기존64문서·8개 용어군을 재사용하는8조건 비교다. Gemma12B와 Qwen27B에
각512회, 총 **1,024회**를 실행한다. 기존 개발/확인 표시는 소스의 이전 분할일 뿐
새로운 독립 확인 자료로 부르지 않는다.

최종 확인 자료는 새로 AI가 작성하고 다른 검토자가 resolver·모델 결과를 보기 전에
검토한96문서·12개 용어군이다. 정의·정답·core/full span과 출처 근거를 먼저 봉인한다.
모든 최종 후보 방법의 원문·프롬프트·실제 token 수까지 진단 생성 전에 고정한다.
AI 합성·AI 검토 자료이며 사람 gold나 실제 업무 분포가 아니다.

진단의 두 모델이 모두 성공하고 원시 응답 재채점·집계 게시가 완료되면 기준선 이외
7가지 방법을 다음 순서로 정렬해 한 방법을 고른다.

1. 두 모델의 잘못된 승인 합계가 적은 순서.
2. 두 모델의 올바른 승인 합계가 많은 순서.
3. 총 입력·출력 token 수가 적은 순서.
4. 사전 지정한 조건 순서.

그 방법과 `paragraph_all_production`만 최종96문서에서 실행한다. 두 모델은 같은
방법과 같은192요청을 사용하므로 최종 **384회**, GPU 생성은 합계 **1,408회**다.
선택 규칙과 선택 근거를 별도 파일로 봉인하고 최종 응답으로 방법을 다시 고르지
않는다. 이 규칙은 진단용 방법 선택이며 배포 위험 제어 또는 오류 상한 보장이 아니다.

## 검증·실행·지표

temperature0, seed0, thinking off, strict JSON, 단일 생성·재시도 없음, 출력 상한
768tokens를 공통 적용한다. 두 실제 tokenizer로 입력과 예약 출력의 합이8192tokens
이내인지 검사하고, 초과하면 원문을 자르지 않고 준비 단계에서 실패한다.

실제 운영 승인 결과와 shadow 승인 결과를 명확히 나눠 제안 정오, 정상 승인 회수율,
오승인, 정당한 기권·과잉 보류, 실패 사유와 채널·속성별 결과를 보고한다. 입력·출력
token 수, p50/p95/p99 지연과 근거 준비 비용을 함께 보존한다. 문서·용어군의
paired 비교를 사용하며 모델 호출 수를 독립 사건 수로 세지 않는다.

모델은 one-server에서 Gemma 다음 Qwen 순서로 실행한다. 다른 GPU 프로세스를
중지하지 않고 자원이 사용 중이면 기다린다. 원시 요청·응답은 비공개로 보존하고
봉인된 원시 응답 재채점 후 집계만 게시한다. 실제 업무 shadow는 입력 전까지
`WAITING_FOR_INPUT`이다.
